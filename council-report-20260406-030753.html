LLM Council Verdict

April 6, 2026 — Four Factors Data Source Priority

Should cbbdata.com API remain the primary source (Strategy 1) for four factors data, or should trank.php CSV be promoted to primary given its server-side date filtering capability?

Advisor Alignment

Contrarian: Promote trank.php
First Principles: Source choice is secondary
Expansionist: Promote trank.php
Outsider: Promote trank.php
Executor: Keep cbbdata primary

Peer review: 4 of 5 reviewers ranked the Contrarian's response as strongest. 3 of 5 flagged the Executor's blind spot.

Where the Council Agrees

The guard is load-bearing and under-tested. Every advisor — even the Executor defending cbbdata — acknowledges the guard is the real protection mechanism. Nobody argued the architecture is safe without it.

Failure mode asymmetry is real. A system that fails loudly when fragile (trank.php with Cloudflare) is safer than one that succeeds quietly when wrong (cbbdata post-tournament with a misconfigured date). Four of five peer reviews confirmed this as the strongest insight.

Where the Council Clashes

Cloudflare fragility: The Executor argues it's active maintenance debt — one update away from silent failure during the exact three-week window that matters. The counter: Cloudflare failure is detectable and loud, while guard misconfiguration is invisible until you audit.

"Write a test" as defense: The Executor calls a guard test structural defense. Three peer reviews reject this — a test passing in CI tells you the guard fires on the date you think is correct. It says nothing about whether that date is actually correct.

Blind Spots the Council Caught

Tournament date provenance (flagged by 4 of 5 reviewers): TOURNAMENT_START_DATES is a hardcoded dict that requires manual update every year. The guard's correctness depends entirely on a human step happening correctly. No test catches a missing or wrong entry for a new year.

Observability (flagged by reviewer 5): Can you audit, after the fact, which source was used and what data the model actually saw? Without provenance tracking, you cannot diagnose a bad bracket season or reproduce model inputs.

Split-use architecture (flagged by reviewer 3): Production inference and feature engineering can use different primary sources. The decision doesn't have to be binary.

The Recommendation

Promote trank.php to primary. Treat Cloudflare fragility as a first-class reliability problem to solve immediately — not later.

The guard's single point of failure is a hardcoded config dict requiring human update every year. When that update is missed or wrong, cbbdata returns contaminated data silently. trank.php with server-side date filtering means even if the guard misfires, the underlying data is already scoped correctly. Two independent correctness mechanisms with different failure modes.

The Executor's Cloudflare concern is legitimate but solvable: browser-like headers, retry logic, integration test confirming endpoint reachability before pipeline execution. Cloudflare failure is loud and detectable. A misconfigured tournament date is silent and catastrophic. Choose the loud failure mode.

Do not promote trank.php because of the Expansionist's feature roadmap. Promote it because the risk surface is smaller.

The One Thing to Do First

Before touching source priority: audit TOURNAMENT_START_DATES. Confirm it has a correct entry for the current year. Add a runtime check that raises an explicit MissingTournamentDateError if the current pipeline year has no entry. Write one test confirming a missing entry is caught before any data fetch occurs.

That single change converts the silent failure mode into a loud one — and exposes exactly how fragile the guard's provenance is, which will make the source promotion decision obvious.

Advisor Responses (click to expand)
The Contrarian

The tournament date guard is a single point of failure protecting you from catastrophic leakage, and you're treating it like a solved problem. If that date is wrong by even one day — a timezone issue, a config typo, someone bumping the tournament start date in a non-obvious place — the API silently returns contaminated data with zero indication anything went wrong.

trank.php's server-side date filtering is architecturally superior for one reason: the contamination protection lives closer to the data source and doesn't depend on your application code being correct. Your guard can have a bug. The trank.php server filtering the data before it even arrives cannot be circumvented by your bugs.

The Cloudflare fragility argument cuts both ways. Yes, trank.php can break. But when it breaks, it breaks loudly. The API's leakage failure mode is silent corruption. Single-layer leakage protection on your most critical features isn't a design — it's a bet.

The First Principles Thinker

The question being asked is "which source is better?" But the real question is: what is the actual leakage risk surface, and does the source choice materially change it?

The guard is a hard error making the API's lack of filtering a non-issue in production. Historical years aren't scraped at all. The source comparison only matters for one narrow window: scraping current-year pre-tournament data. In that window, both sources work. trank.php's server-side filtering is redundant given the guard already exists.

The real risk is cache contamination. The question doesn't fully address whether cache invalidation is enforced at prediction time. Source choice is secondary architecture. Cache integrity is primary.

The Expansionist

trank.php isn't just "more robust leakage protection" — it's a richer data pipeline. Server-side date filtering means you can trivially generate rolling snapshots: Four Factors at week 4, week 8, week 12, conference tournament start. That's trajectory data. How a team's eFG% defense trends into March is a fundamentally different signal than their season aggregate.

If trank.php supports arbitrary begin/end date windows, you can construct conference-schedule-only splits, exclude non-conference cupcakes, or build momentum features over the final 10 games. Once you normalize on a date-parameterized source, you can backfill historical snapshots consistently. Promote trank.php. Then ask what other features support date windowing.

The Outsider

No date filtering + one guard = one lock. Server-side filtering + guard = two locks. When the cost of failure is "your model is secretly cheating and you won't know it," you want more locks, not fewer.

The cbbdata.com argument is a formatting preference. You're trading structural safety for convenience of parsing. The Cloudflare concern is a reliability problem, not a correctness problem. A system that fails loudly when fragile is safer than a system that succeeds silently when wrong. Promote trank.php. Fix the fragility separately.

The Executor

Keep cbbdata.com as primary. The guard is a hard error — auditable with one test. trank.php's Cloudflare dependency is active maintenance debt. Promoting it to primary means you're one Cloudflare rule update away from a silent failure during the exact three-week window this system matters.

Write a single test that fires the guard with a mocked date of tournament start + 1 day and confirms it raises LeakageError. That test is your actual protection. The source debate is secondary to that. Keep cbbdata primary. Fix the guard test. Ship it.

Peer Review Highlights (click to expand)

Strongest advisor (consensus): The Contrarian (selected by 4 of 5 reviewers) — identified the most dangerous failure mode: silent data corruption from guard misconfiguration.

Biggest blind spot (consensus): The Executor — equated "auditable" with "reliable" and treated a CI test as structural defense. A test can't catch a wrong tournament date in config.

What all five missed:

  • Guard provenance: Where does the tournament date come from? It's a hardcoded dict requiring yearly manual update. That human step is the real single point of failure. (4 reviewers)
  • Observability: No advisor asked whether the system can audit which source was used and what data the model actually saw at inference time. (1 reviewer)
  • Split-use architecture: Production inference and feature engineering can use different primary sources. The binary framing is artificial. (1 reviewer)
