LLM Council Report

5 Advisors · 5 Peer Reviews · Chairman Synthesis · April 2, 2026

"In the march-madness-forecaster repo, besides building a backtest harness, what should be the #1 priority to improve the project?"

The Recommendation

Wire the seed-only baseline into the LOYO evaluation loop and run it. This is the single highest-leverage action because it produces a binary decision gate:

  • If the pipeline does NOT beat seed-only at p < 0.05: Most of the 122K lines, 58 tuned constants, and 40 enable flags are noise. The correct next step is radical simplification — strip to logistic regression on 3-4 features, delete everything else.
  • If the pipeline DOES beat seed-only significantly: You have proof of value and can proceed to the deletion pass knowing what matters.

This takes priority over deletion because deletion without measurement is guessing. The baseline comparison tells you which components earn their complexity.

Caveat: With 58 tuned constants and ~65 evaluation games, the pipeline may "win" due to overfitting the evaluation set. Consider using a fully held-out year that was never used during tuning.

The One Thing to Do First

Wire seed_baseline_probability into the existing LOYO loop in loyo_protocol.py, collect per-fold Brier scores for both seed baseline and full pipeline, and run a paired statistical test. Do not tune anything. Do not clean anything. Do not delete anything. Just measure.

Where the Council Agrees

  • The Executor wins unanimously. All 5 peer reviewers independently ranked the seed baseline comparison as the strongest proposal.
  • The Expansionist is sequentially wrong. Every reviewer flagged market integration as the worst idea right now — adding complexity to an unverifiable codebase.
  • Deletion is necessary but secondary. Three advisors converge on ruthless deletion, but reviewers rank it behind measurement.
  • The codebase is untrusted. Stacking leakage found. README contradicts config. Four predict_probability methods exist. No advisor defended the current state.

Where the Council Clashes

Delete first vs. measure first. The Contrarian/First Principles say: clean so the harness can be built correctly. The Executor says: measure now, because deletion without data is aesthetic preference. The Executor's path is faster and produces a decision gate — if the pipeline doesn't beat seed-only, the deletion conversation becomes "delete almost everything."

How much is salvageable. The Outsider/First Principles imply very little. The Executor assumes core LOYO machinery works enough for a valid comparison. If leakage contaminates the evaluation loop itself, the one-day estimate becomes optimistic.

Blind Spots the Council Caught

  • The overfitting math is damning. 58 tuned constants on ~60-70 games per fold is a statistical impossibility. The project may need fewer parameters, not fewer files. Realistic capacity: 5-8 parameters.
  • Power analysis is missing. Confidence intervals on Brier differences at N=60 are wide. The baseline comparison may be inconclusive.
  • Calibration sample size is a hard constraint. No code change fixes this. The project should adopt wide confidence intervals as a permanent feature.
  • No test suite. Deletion without tests risks breaking production silently. No safety net for refactoring exists.
The Contrarian (full response)

The fatal flaw: you cannot evaluate whether your pipeline is correct because the codebase is too complex to audit. The stacking leakage bug proves this — it existed in production and required a council to find it. How many more are hiding in 535 files?

The backtest harness will be wrong if built on this foundation. You'll wire it into the wrong predict_probability method (there are at least four). You'll test the wrong code path and declare victory.

Priority one: ruthlessly delete everything not on the production path. Archive the GNN, transformer, research loop, womens pipeline, and agent orchestration into a separate branch. Get the production pipeline down to something a single person can read top-to-bottom in an afternoon.

A model you can't audit is a model you can't trust. No amount of clever features fixes that.

The First Principles Thinker (full response)

You don't have a prediction system. You have 122,000 lines of code wrapping a logistic regression. The system's complexity has outrun its epistemic foundation.

Strip to first principles: You know ~17,600 regular-season outcomes and ~530 tournament games. Every line of code beyond what's needed to extract signal from that data is either extracting real signal or overfitting noise.

The #1 priority is a ruthless deletion pass. Establish bare-minimum baseline, re-enable each component ONE AT A TIME, measure marginal Brier improvement. Anything below threshold gets deleted — not disabled, deleted. The 40 enable flags are a code smell.

The real question isn't "what should we add?" It's "how much can we remove before prediction quality drops?" The answer will be sobering and informative.

The Expansionist (full response)

Build a real-time market integration and public pick exploitation layer. Market prices are the single strongest predictor of tournament outcomes — stronger than any feature engineering with box scores. Your logistic regression fights for the last 2% of signal. Markets hand you the first 80% for free.

The contrarian EV optimizer only works if your crowd model is accurate. A properly calibrated crowd model turns your whole simulation stack from "interesting exercise" into "actual edge."

Market data solves your calibration crisis. Sportsbooks have calibrated against millions of dollars. Blending with market-implied probabilities gives you calibration for free.

The move: build a robust multi-source market data pipeline with historical backfill, replace hardcoded 0.20 blend weight with learned weight, use model-vs-market divergence as a feature.

Note: This proposal was unanimously rejected by all 5 peer reviewers as sequentially wrong — adding complexity to an unverifiable, leaky codebase.

The Outsider (full response)

I have no idea what this project actually does when I look at it, and that's the problem.

You have 535 Python files. A README that lies about what the system does. Research modules that are disabled. Production config that enables features the documentation doesn't mention.

My #1 priority: Delete everything that isn't production. Not disable. Delete. You can't fix calibration if you can't see what the calibration code touches. You can't verify stacking contamination if you're not sure which stacking implementation is live.

Strip it to what runs in production. Make the README match reality. Get to a point where someone with zero context can open the repo and understand the pipeline in 15 minutes. Then improve it.

Complexity you can't explain is complexity you can't trust.

The Executor (full response)

The #1 priority is building and running the seed-only baseline comparison end-to-end. The pieces exist: src/evaluation/baselines.py defines seed_baseline_probability(), and src/ml/evaluation/loyo_protocol.py has the LOYO infrastructure. But there's no evidence these are wired together.

58 tuned constants against ~440 evaluation games gives a DoF/sample ratio of 0.13 (target is <0.01). You literally cannot tell if your full pipeline beats seed-only.

Concrete steps: wire seed_baseline_probability into the LOYO loop, run both through identical folds, collect per-fold Brier scores, apply compute_ablation_threshold to the paired differences.

If the full pipeline doesn't beat seed-only at p<0.05, everything else is noise. This takes a day, not a week. And the answer determines every decision that follows.
