Where the Council Clashes

Gap 2 (team_metrics): The Outsider treats it as an uninvestigated risk. The Executor dismisses it. Resolution: trace every code path to confirm team_metrics is unreachable from the backtest. This is a factual question with a deterministic answer.

Gap 3 (tournament games in historical_games): The Expansionist sees untapped signal. The Contrarian sees a convention that will fail. Compatible positions: tournament games can be valid signal if accessed through a guarded interface, not a trust convention.

The 0.95 R² threshold: Peer reviews flagged aggregate R² as the wrong metric. It can hide systematic divergence on mid-major and unusual-tempo profiles — exactly where upsets cluster. Profile-stratified residuals matter more.

Blind Spots the Council Caught

Researcher degrees of freedom: Clean files don't reset researcher memory. If hyperparameters or feature choices were tuned while observing backtest results on those same years, the backtest is optimistic regardless of data cleanliness.

Pre-purge model contamination: Purging files prevents future contamination. If model weights were fit on contaminated data before the audit, purging does not un-train them. Were models retrained from scratch?

Backtest scoring validity: If the scoring function doesn't model real pool dynamics — field size, chalk distribution, tiebreakers — clean data and accurate predictions still fail to predict pool performance.

The Recommendation

Run the Torvik correlation check before trusting any backtest result. Aggregate R² against published Torvik ratings for 2019-2023 is the starting point. Stratify residuals by team profile: mid-majors vs. power conferences, high-tempo vs. low-tempo, top-25 seeds vs. mid-seeds. Systematic divergence in any stratum means a biased model, not just an approximate one.

Simultaneously: trace team_metrics code paths (afternoon task). Add noseed_model runtime guard (20-minute fix). Confirm whether pre-purge contaminated data trained any model artifacts — if yes, rebuild from scratch.

The One Thing to Do First

Pull published Torvik ratings for 2019-2023 and run your locally-computed barthag against them — stratified by seed range and conference tier, not just in aggregate.

Everything else depends on: are you backtesting Torvik, or something else? If correlation is clean across all strata, proceed with confidence. If not, the leakage audit is the second problem. Model validity is the first.

Advisor Responses

CONTRARIAN Runtime guards ≠ documentation; correlation check required

Gap 1 is the one I'd bet money on biting you. "Files are clean" is a statement about the present. Runtime guards are statements about the future. Someone adds a new Torvik file, forgets the date-filter convention, and _load_team_stats() silently ingests it. "Low risk" without a runtime check is not low risk — it's undetected risk.

Gap 3 is worse than it sounds. "Downstream code must apply its own date filter" is a design philosophy, not a constraint. That's the same logic as "developers should write secure code." It will fail.

The Pythagorean exponent and iteration count: you're approximating an approximation and validating against outcomes that the real Torvik methodology might predict differently. You need a direct correlation check. If R² isn't above 0.95, you're not computing Torvik — you're computing something else with a borrowed name.

FIRST PRINCIPLES You're answering the wrong question

The audit answers "do we have leakage?" when the real question is "are our backtest results meaningful?" Your approximation may diverge precisely where it matters: mid-majors, late-season momentum, unusual tempo profiles. Tournament upsets cluster in exactly these edge cases.

The first-principles question: what are you actually backtesting? If locally-computed barthag diverges 15-20% on certain profiles, it's an unknown model wearing Torvik's label. The Pythagorean exponent and iterations are load-bearing assumptions, not implementation details.

Run locally-computed barthag against published Torvik for 2019-2023. If below 0.95, no amount of leakage prevention fixes the accuracy problem.

EXPANSIONIST Divergence is information, not just error

If locally-computed metrics diverge from real Torvik, that divergence is information. You might have accidentally discovered a better version. Systematic divergences for specific team profiles tell you where real Torvik is also uncertain — a competitive edge to exploit.

Gap 3 is undervalued: tournament games in historical_games are an untapped training signal for tournament-specific performance patterns that regular-season data cannot capture. The backtest isn't the end product — it's the floor.

OUTSIDER "Not used" needs to be proven, not asserted (rated strongest by all 5 reviewers)

Gap 2: "is not used by backtest" — how do you know? Was this confirmed by tracing every code path, or by reading the description of what the backtest is supposed to do? Data files that "aren't used" have a way of getting used — by a helper function, by a fallback, by a future change nobody remembered to audit.

Gap 4: has anyone actually compared the locally-computed approximation against real Torvik numbers for even one year? A systematic bias could corrupt predictions in patterned ways backtest results would never reveal.

"Files are clean" and "not used by backtest" need to be proven, not asserted.
