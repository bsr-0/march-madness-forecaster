April 2, 2026 — 5 advisors, 5 peer reviews, 1 verdict

Question: What are the biggest limitations of the March Madness Forecaster repository?

Advisor Alignment

Contrarian

Where the Council Agrees

BSS ≈ 0 is the defining fact. Every advisor identifies that the system produces predictions no better than seed-based lookup. The 123K lines, 537 source files, and disabled infrastructure are all downstream of this single failure.

The codebase is massively oversized for what it delivers. Whether framed as "monument to sunk cost," "empty safe with bank-vault security," or "active liability" — every advisor agrees the ratio of code to value is indefensible.

The quality controls are theater. 20% test coverage, suppressed lint rules (F401/F841/F821), and no meaningful type checking. Suppressing F821 (undefined names) means the linter is configured to ignore code that literally cannot run.

The disabled infrastructure is dead weight, not latent value. Four of five advisors agree GNN, transformers, and ensemble stacking being disabled is a liability, not an asset. Peer review unanimously identified the Expansionist's dissent as the weakest position.

Where the Council Clashes

Is there signal beyond seeds, or is this an information-theoretic wall?

The Contrarian and First Principles Thinker argue tournament basketball has roughly 4 bits of entropy per game that seeds don't capture, and extracting it from 530 games may be fundamentally impossible. The Expansionist counters that Vegas lines demonstrably beat seed baselines, proving exploitable signal exists.

Peer review resolution: Vegas beats seeds using real-time injury reports, line movement, and betting market information — not historical box score features. The signal Vegas exploits is unavailable to a system that trains on historical data.

Should the disabled infrastructure be revived or deleted?

The Expansionist says revive it. The Executor says archive it. The Contrarian says it's sunk cost. The peer reviews unanimously sided against revival without new evidence.

Blind Spots the Council Caught

Silent data bugs are a real possibility. 20% coverage + suppressed F821 means the pipeline could contain data processing errors that silently corrupt features. BSS ≈ 0 might reflect buggy features, not an information-theoretic ceiling.

Feature collinearity with seed strength. The 7 selected features may all be proxies for seed strength. If every feature is seed-with-noise, logistic regression on those 7 is mathematically equivalent to seed baseline — BSS ≈ 0 becomes tautological.

Bracket optimization is the actual product. Game-level BSS ≈ 0 does not mean zero value in a bracket pool. Small calibration advantages compound across 63 games. Identifying correlated upsets can produce bracket strategy that wins pools.

The LOYO evaluation is statistically underpowered. 530 tournament games across 9 folds = ~59 games per test fold. Confidence intervals on BSS at that sample size are enormous. The "simple model is the ceiling" conclusion was drawn from data that cannot support it.

The Recommendation

This project needs a hard reset on scope, not more model complexity.

  1. Acknowledge the product is bracket strategy, not game probabilities. Reframe the success metric around bracket pool optimization.
  2. Audit for silent data bugs before drawing any conclusions about model ceilings. With 20% coverage and suppressed F821, you cannot trust features are computed correctly.
  3. Cut the codebase to what runs in production. Archive everything disabled. Target under 15K LOC. Remaining code should have 80%+ coverage and zero suppressed lint rules.
  4. Check feature independence from seed. If all 7 features correlate at r > 0.8 with seed, BSS ≈ 0 is uninformative.

Do not revive GNN/transformer/ensemble infrastructure until you have confirmed the simple pipeline is bug-free and features provide independent signal.

The One Thing to Do First: Run a correlation matrix of your 7 production features against seed number, on your training data, and publish the result. If the features are all highly correlated with seed (r > 0.7), then BSS ≈ 0 is expected and meaningless — you've been regressing seed proxies against a seed baseline. If they're genuinely independent and BSS is still ≈ 0, that's real evidence of an information-theoretic ceiling, and the project should pivot entirely to bracket optimization strategy. Either answer changes everything. It takes 20 minutes to compute.

Advisor Responses

The Contrarian

The fatal flaw is BSS ≈ 0 versus seed baseline — this entire system produces predictions no better than looking up seed matchup win rates. The "simple model is the ceiling" claim is self-serving nonsense — that conclusion was reached using LOYO on 530 tournament games, roughly 59 games per fold. You cannot draw reliable conclusions about model superiority with 59-game test sets. The error bars on BSS at that sample size swallow any signal. The project declared defeat prematurely, then built 123K lines around that declaration.

The codebase is a monument to sunk cost — GNN, transformer, ensemble all disabled. The quality controls are performative — 20% coverage is meaningless, suppressing F401/F841/F821 means the linter ignores bugs, mypy checks nothing.

The real limitation: tournament basketball has roughly 4 bits of entropy per game that seeds don't already capture. The honest next step is either find genuinely novel data sources or accept the seed baseline and focus on bracket optimization strategy.

The First Principles Thinker

The question isn't "what are the limitations." The question is: why does 123K lines of code exist to deliver a model that can't beat picking by seed? BSS ≈ 0 means the system produces no value beyond a lookup table.

The actual problem is information-theoretic — March Madness outcomes contain very little predictable signal beyond seed strength. Seeds already encode committee judgments aggregating hundreds of data points. You're trying to extract residual alpha from ~530 tournament games.

The real limitations: 1) Wrong success metric — BSS against seed baseline is the hardest benchmark. The system should measure value-add in bracket pool contexts, where small edges compound across 63 games. 2) Wrong unit of prediction — game-level probabilities are commoditized. The scarce value is in identifying correlated upsets. 3) No feedback loop — nine years of predictions with no systematic analysis of where the model fails.

The Expansionist

The massive untapped upside: you built the infrastructure for a much more powerful system and then gave up at the logistic regression. BSS ≈ 0 is not a ceiling — it's a signal that 7 features from logistic regression can't extract the edge that exists. The architecture doc declaring "the simple model is the ceiling on this data" is the single most dangerous sentence in the codebase.

The biggest limitation is that 86 features, GNNs, transformers, and ensemble stacking exist but are disabled. Feature selection going from 86 to 7 likely discarded interaction effects. The scraping infrastructure is an unrealized asset — injury reports, transfer portal data, player-level metrics create edge in March specifically.

The codebase is 80% of the way to a competitive prediction system. What's missing is the willingness to let complex models fail expensively until they don't.

The Outsider

You built a 123K-line monument to a conclusion you already reached. The 20% coverage threshold is a confession — 79K lines of tests but only 20% coverage means large sections are untestable. The lint suppressions for undefined names and unused variables reinforce this.

BSS of approximately zero is the only number that matters, and you're burying it. The scraping infrastructure concerns me most — how many scrapers actually connect to production? The governance system is solving the wrong problem — bank-vault security around an empty safe.

This looks like a research project that kept adding complexity hoping something would stick, then locked down the one thing that worked (barely). The priority isn't improving the model — it's deciding whether 90% of this code should exist at all.

The Executor

Actionable limitations ranked: 1) Model can't beat seeds — run feature importance on all 86 features against tournament outcomes specifically. 2) 530 tournament games is the real bottleneck — add data back to 2002, add NIT/CBI as auxiliary signal. 3) 123K LOC is active liability — archive non-production code, get under 20K LOC. 4) 20% test coverage means you can't safely change anything — get to 80% on the 7-feature pipeline. 5) Audit which scrapers feed production, kill the rest.

Stop building infrastructure. Start beating seeds.

Peer Review Highlights

Strongest response (unanimous): The Contrarian — for identifying that LOYO on 59-game folds cannot reliably distinguish models, undermining the "ceiling" conclusion.

Weakest response (unanimous): The Expansionist — assumes the edge exists without evidence, advocates expensive exploration without addressing the sample size problem.

Key blind spots caught:

  • Silent data bugs are likely in a pipeline with 20% coverage and suppressed F821
  • 7 features may be collinear proxies for seed — BSS ≈ 0 could be tautological
  • Bracket pool optimization is the actual product, not game-level BSS
  • Model may be well-calibrated in specific matchup bands (5v12, 7v10) even with overall BSS ≈ 0
  • No defined deployment target or product scope drives requirements
