LLM Council Verdict

5 advisors · 5 peer reviews · chairman synthesis

Question: What is the single biggest limitation of the March Madness Forecaster repository, and what should be prioritized to fix it?

Where the Council Agrees

Stacking weight contamination is a validity crisis, not a code quality issue. Four of five advisors — and all five peer reviews — converged on this independently: the ensemble stacking layer was optimized on the same LOYO predictions used to evaluate it. Every confidence metric, Brier score, and calibration plot is reporting on a system that has implicitly seen its own holdout signal. The governance system then cryptographically locks in whatever is broken, making the contamination official.

There was also broad agreement that the 139k-line monolith files are a serious structural problem — but disagreement on whether it is the problem.

Where the Council Clashes

Fix the validity problem first, or fix the readability problem first?

  • Validity camp (Contrarian + First Principles): The calibration and stacking contamination mean you currently don't know if your model is better than a coin flip. Refactoring a broken model into clean modules gives you a clean, readable system producing invalid predictions.
  • Readability camp (Outsider + Executor): You cannot safely fix calibration or stacking in a 139k-line file you cannot reason about. Refactoring is a prerequisite for any meaningful repair.

Resolution: The stacking fix is narrower than a full refactoring job. You do not need to understand all 139k lines to locate and refit one stacking function.

The Expansionist's position (activate GNN/transformer research) was identified by all five peer reviews as the weakest — building experiments on a contaminated evaluation harness launders overfit signal, not real gains.

Blind Spots the Council Caught

  • Scraper fragility as silent upstream failure. Every advisor assumed training data is trustworthy. All five peer reviews flagged this. Fragile web scrapers with no validation layer mean features may be silently corrupted — and a perfectly calibrated model fed bad data is still worthless.
  • No revoke-and-relock protocol. The governance system has no documented path to invalidate a production lock once contamination is discovered. The system designed to prevent bad predictions from shipping may now be preventing a necessary correction.
  • Cost of delay — the tournament is live right now. Today is March 31, 2026. Every fix proposed is post-tournament. The immediately actionable question: what monitoring should be running now to capture ground truth?

The Recommendation

The single biggest limitation is stacking weight contamination. It should be fixed before any architectural work. The 139k-line file is a serious operational hazard but a second-order problem — it makes the fix harder, but doesn't change what needs fixing.

  1. Now (this week, during live tournament): Instrument outcome capture. Log every prediction against actual game results. This costs almost nothing and gives you clean 2026 ground truth.
  2. Post-tournament (April): Locate and refit the stacking layer using only genuinely out-of-fold predictions from a strict temporal split. Re-run holdout evaluation. Determine if the model actually outperforms a simpler baseline.
  3. After validity is confirmed: Nest calibration inside LOYO folds. Add data quality validation on scraper outputs. Then refactor baseline_training.py.
  4. Only after the above: Consider research infrastructure activation (GNN, transformers).

The governance lock should be reviewed for a revoke-and-relock protocol. Locking a contaminated model with cryptographic certainty is not safety — it is false confidence institutionalized.

The One Thing to Do First

Add outcome logging to the live tournament pipeline today. Capture every prediction the model makes and the actual game result, stored in a format you can use for post-tournament evaluation. The tournament is live. You cannot fix stacking contamination mid-tournament. But you can ensure that when it ends, you have clean ground truth to validate against. Every other fix requires the tournament to be over. This one doesn't.

Advisor Responses

The Contrarian

The stacking weights optimized on the same LOYO predictions used for evaluation is not a "moderate" issue — it's a fundamental validity problem that corrupts every confidence metric the system produces.

The ensemble weights were tuned on the very predictions being evaluated, meaning the stacking layer has been implicitly fit to your holdout signal. The LOYO CV that should prevent this becomes theater. Your calibration plots, your Brier scores, your confidence intervals — all of them are optimistic by an unknown amount.

The massive file sizes (139k line baseline_training.py) aren't just technical debt — they're evidence that nobody can actually audit what's happening inside. The governance system locks in whatever is broken with cryptographic certainty.

Priority: Refit the stacking layer using a strict temporal split where ensemble weights are determined solely on years prior to the evaluation period. Then re-run 2025 holdout evaluation from scratch.

The First Principles Thinker

The question assumes there's a single "limitation to fix." That framing is wrong. The core failure mode is epistemic opacity — you cannot trust any output because you cannot verify where signal ends and leakage begins.

Calibration isn't nested, stacking weights are optimized on same predictions used to evaluate them. The system's confidence estimates are systematically overfit. Your 50,000 simulations are precision theater. You're multiplying garbage by 50,000 and calling it rigor.

The real question isn't "what's the biggest limitation?" It's "do the probabilities coming out of this model mean anything?" Right now, you don't know.

Priority: Nested calibration within LOYO folds, and stacking weights optimized on genuinely out-of-fold predictions only.

The Expansionist

The disconnected research infrastructure is the most criminally undervalued asset here. GNNs, transformers, and agent orchestration sitting dormant while the production system runs an 8-season ensemble with known leakage.

Graph neural networks on tournament brackets capture conference strength, scheduling effects, and team interdependencies in ways that 79-dimensional flat features fundamentally cannot. Agent orchestration that dynamically adjusts priors mid-tournament could be transformative.

The leakage issue and massive files are maintenance problems — important, but fixing them doesn't expand what's possible.

Priority: Build a clean activation pathway for the GNN/transformer experiments, wire them into the ensemble, and measure whether they outperform on the 2025 holdout.

Note: All 5 peer reviews identified this as the weakest position — activating research on a contaminated evaluation harness produces meaningless benchmarks.

The Outsider

The 139,000-line baseline_training.py file is the single biggest limitation, and it's not close. That's not a file — that's a system that ate its own documentation and swallowed its own boundaries.

When something breaks, where do you look? When you want to change something, how do you know what else you're touching? You don't. You guess, you test, you hope.

Everything else — calibration leakage, stacking contamination, scraper fragility, disconnected research — those are problems you can fix once you can see the code clearly. You cannot fix what you cannot read.

Priority: Break baseline_training.py into modules with explicit interfaces.

The Executor

The biggest limitation is baseline_training.py at 139k lines. Full stop.

Monday morning: run grep for top-level functions/classes, identify 5-10 clearest functional boundaries (data loading, feature computation, model training, evaluation, serialization), extract one module at a time, regression test against frozen baseline.

The calibration and stacking issues require understanding what the code actually does — you cannot safely fix a calibration pipeline you cannot read. The production freeze is helpful — use it as a regression baseline while refactoring.

Priority: Fix the file size problem first. Everything else is downstream of being able to read your own code.
