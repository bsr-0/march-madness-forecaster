LLM Council Report

Training Data Strategy for Data Starvation — April 1, 2026

Prior Council Correction The previous council stated the system trains on "~400 tournament games." This was wrong. The system already trains on ~2000-2200 effective samples (regular season + tournament games, 8 years, symmetric augmentation). The data starvation problem is real but manifests differently than described: in LOYO validation (8 folds), stacking meta-learner (known overfit, re-enabled anyway), calibration (60-70 holdout games), and distribution mismatch between regular season training and tournament deployment.
Question Counciled Should this repo train on regular season games in addition to tournament games? How can it best address data starvation given that the system already uses ~2000 regular season + tournament samples but deploys on a fundamentally different game type (neutral site, single elimination, seeded)?

The Recommendation

The core problem is distribution mismatch, not data starvation. Adding more regular season samples does not fix a tournament-inference problem — it potentially worsens it by burying tournament signal under 2000x more regular season noise.

Do three things:

  1. Fix calibration properly. Replace the single-year holdout (60-70 games) with out-of-fold tournament predictions across all available years using LOYO-CV. This turns 60-70 games into the full historical tournament sample. Highest-ROI fix in the repo.
  2. Run the tournament-only baseline experiment. Train on tournament games only (~500-600 from 2005-2024) with a simpler model (logistic regression or shallow tree). Compare against the current blended model. This is diagnostic, not deployment — if the simple model matches or beats the ensemble, the entire architecture is wrong.
  3. Extend historical years to 2005-2024 for tournament games specifically. The data is on disk. Tournament games only — not regular season. This gets calibration from 60 games to ~300-350.

Disable stacking until base model quality justifies it. If you need stacking to be competitive, your features aren't doing enough work.

Do NOT:
  • Add NIT or conference tournament data (different distribution disguised as similar)
  • Expand regular season samples (more noise, not more signal)
  • Change late_season_training_cutoff until after the tournament-only experiment

The One Thing to Do First

Run the tournament-only model experiment. Train on ~500 tournament games (2005-2024) with a logistic regression. Compare Brier score against the current 2200-sample stacked ensemble.

If 500 tournament games with logistic regression outperforms 2200 blended games with a stacked ensemble, the current training data strategy is actively harming the model. This resolves the core debate with data instead of argument. One afternoon of work.

  • Stacking "disabled for overfitting, re-enabled anyway" is a red flag everyone noticed

Where the Council Clashes

Expansionist vs. Everyone: NIT/conference tournament data. The Expansionist proposed adding ~200+ NIT games/year as "structurally identical" to March Madness. Four out of five peer reviewers rejected this outright: seeding logic, stakes, field quality, and pressure differ systematically. Adding NIT data introduces a new distribution problem while pretending to solve the old one.

Executor vs. Contrarian: Extending historical years. The Executor calls extending to 2008-2024 a cheap win. The Contrarian says it's more of the same bad data. Resolution: extending tournament games specifically to 2005-2024 is defensible. Extending regular season data is not.

Unresolved: classification vs. simulation. Should this be treated as a per-game classification problem with better features, or a distribution-aware inference problem with a simpler model trained only on tournament data? This is consequential and unresolved. The tournament-only experiment is designed to answer it.

Blind Spots the Council Caught

  • Within-tournament distribution shift. R64 and Elite 8 are structurally different games. A model calibrated on aggregate tournament games averages across different round dynamics. CV should stratify by round, not just by year.
  • Target variable path-dependence. If predictions feed forward through a bracket simulation, errors compound autoregressively. Whether this is a classification or simulation problem determines the architecture.
  • Cold-start problem. ~40% of D1 programs appear zero or one times in tournament history. If any features encode team identity rather than team-agnostic metrics, the model memorizes rather than generalizes.
  • Stacking re-enablement as diagnostic. Someone judged accuracy gain outweighed overfitting risk — implying base model standalone accuracy was unacceptable. That's the real problem to solve.

Advisor Responses

The Contrarian — "Distribution mismatch, not data starvation"

"Data starvation" implies more data solves the problem. It doesn't. The real issue is distribution mismatch, and throwing more regular season samples at it makes the problem worse. Seeds don't exist in November. Neutral sites are rare. No team is playing for survival.

The round-weighting (R64=1 → NCG=32) is the only honest signal, and it's fighting a losing battle against 2000x more regular season samples. That ratio is the problem, not the absolute count.

The stacking meta-learner "disabled by default because it overfits to ~400 samples" is a confession, not a mitigation. Enabling it in production anyway is a known liability someone decided to ship.

Calibration on 60-70 tournament games is noise fitting. One unusual tournament run shifts the calibration entirely.

What's missing: any honest answer to "what does this model actually learn that's tournament-specific?" If the answer is "not much," the correct fix is a fundamentally different architecture that treats tournament games as a separate inference problem.

The First Principles Thinker — "Feature engineering over data augmentation"

The question is framed as "data starvation." That's a symptom label, not a diagnosis. The real constraint: distribution mismatch.

Tournament games are rare by definition — 67 per year. You cannot manufacture that signal. Any attempt to generate "tournament-like" games encodes your own assumptions about what makes them different, which is circular.

What actually helps: (1) Feature engineering over data augmentation — seeds, bracket position, rest days, neutral site indicator explicitly encode the distribution gap. (2) Calibration is the most tractable fix — use all historical tournament games with proper CV instead of one holdout year. (3) Disable stacking or replace with simple weighted average. (4) LOYO variance at 8 folds is honest signal that the problem is hard, not a flaw to engineer away.

The question to keep asking: are we reducing real uncertainty or just hiding it?

The Expansionist — "NIT and conference tournaments are untapped signal"

Everyone's treating this as data poverty. It's signal poverty — different solutions.

NIT and conference tournament games are elimination-format, neutral-site, single-elimination — structurally identical to March Madness. ~200+ NIT games per year = 3x increase in tournament-context data.

Historical seeds can be reconstructed via KenPom or NET rankings. The stacking meta-learner's bottleneck trains on calibrated OOF predictions from games that match tournament conditions. Calibration goes from 60-70 games to 3-4x.

Peer review outcome: 4/5 reviewers rejected this. NIT seeding, stakes, field quality, and pressure differ materially from March Madness. "Structurally identical" was rated the most overconfident assertion in the council.

The Outsider — "An honesty problem"

The numbers add up to an honesty problem, not a confidence problem. Stacking "disabled then re-enabled" = shipping something known broken.

The domain gap is the real issue. What happens if you throw out most of the regular season data and only train on tournament games, even with far fewer samples? A simple model trained on 500 relevant examples often beats a complex model on 2000 irrelevant ones.

The honest answer to "should we change how we handle training data" is: yes, but the first change is admitting that more data infrastructure won't fix a domain mismatch. That requires either getting more tournament data (historical records go back decades) or building a simpler model honest about what it doesn't know.

The Executor — "Three Monday morning moves"

(1) Extend training years to 2008-2024 — ~2000 more samples from data already on disk. One config change.

(2) Drop late_season_training_cutoff_days to 0 or 20 — currently throwing away ~60% of regular season games.

(3) Fix calibration via OOF tournament predictions from CV across all years instead of single holdout split. 60-70 games is not a calibration dataset.

Don't touch stacking or round weights until cheap wins are measured.

Chairman assessment: Correct on calibration fix and extending years. Wrong to add more regular season data before knowing if regular season data helps or hurts.
