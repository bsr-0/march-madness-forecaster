April 4, 2026 • Next Step After Data Pipeline Fix • 5 Advisors • 5 Peer Reviews

The Question

We just fixed the ESPN team-name matching bug (100% match rate, silent fallback removed). Last backtest with broken data showed near-random performance. What should we do next?

Chairman's Verdict

Where the Council Agrees

5/5 Unanimous

Re-run the stochastic backtest with clean data. No one argues for skipping it. No one argues for building features first. This is the single highest-value action.

5/5 Unanimous

Everything else is premature. Contrarian signals, P(rank=1) optimization, file cleanup, blend weight tuning — all wait until the number is in.

Where the Council Clashes

Contrarian vs Executor

"Prepare to quit" vs "Prepare to diagnose." Contrarian and First Principles want a kill criterion — bad number means walk away. Executor says bad number means run ESPN-only diagnostic variant. Executor wins: a single bad number from a system with multiple known issues isn't kill-worthy, but it IS redirect-worthy.

Expansionist isolated

Expansionist assumes the answer before asking. Treats backtest as a formality before mining ESPN data. 4/5 peer reviewers flagged this as the weakest position.

Blind Spots Caught in Peer Review

  • No success threshold defined. Without a pre-committed number, you'll rationalize whatever comes out. "Better than random" is not a threshold. Need a specific metric and cutoff BEFORE running.
  • Sample size reality. 19 years = 19 data points for portfolio outcomes. Statistical power for P(rank=1) is brutally low. May not distinguish real edge from noise in backtest alone.
  • ESPN data circularity. ESPN data is used for both game probabilities AND opponent modeling. Optimizing partially against yourself. Not a showstopper, but needs examination if edge appears — the edge might be an artifact.

Step 1: Re-run stochastic backtest with clean ESPN data (~30 min)

Compare against previous baseline (mean rank ~490/1000). This is the go/no-go gate.

Step 2: Run ESPN-only (100/0/0) variant (~30 min)

If full blend is near-random but ESPN-only shows signal → blend weights are the problem. If both near-random → issue is deeper. Doubles information for same time investment.

Step 3: Do NOT fix stacking contamination yet.

Bundling muddies the measurement. Isolate the effect of the data pipeline fix first. Sequential isolation, not parallel fixes.

The One Thing to Do First

Write down the success threshold — then run the backtest.

Median rank below 400/1000 to continue. Read the number. Everything else follows from that number or is premature without it.

Advisor Responses

The Executor Executor STRONGEST 4/5

Step 1: Re-run the backtest. Right now. 30 minutes. Every other decision is meaningless until you see what the numbers look like with clean data.

Step 2: If the baseline still stinks, run the 100/0/0 ESPN-only variant. Another 30 minutes. If pure ESPN data outperforms the 60/30/10 blend, your blend weights are actively hurting you.

Step 3: If the baseline looks reasonable, fix stacking contamination. If future data is leaking into your backtest, your numbers are lying.

Sequence: measure → diagnose → fix leaks → then build features.

The Contrarian Contrarian

Re-run backtest immediately. Everything else is premature. If results still near-random, the game theory pivot is built on nothing.

The uncomfortable question: what if ESPN public picks simply don't contain enough exploitable information to beat a pool? What if the public isn't wrong enough, often enough, in ways that matter?

Run the one experiment that tells you whether anything downstream is worth building.

The First Principles Thinker First Principles

Do you have evidence this works? You don't. A pool optimizer needs better-than-public estimates AND a leverage strategy. ML adds zero value (BSS=0). Where are better estimates coming from?

Run backtest. But set a kill criterion BEFORE running. At what point accept bracket pools are too luck-dominated for systematic edge? Need that number before the test, not after.

The Outsider Outsider

Last measurement showed random. You don't know if that was the broken data or something fundamental.

Why isn't option 6 (stacking contamination) bundled with option 1? Another known bug means untrustworthy results.

Options 3, 7, 8 sound like avoiding looking at a number that might kill the approach. Run the test. Read the number. Then decide.

The Expansionist Expansionist

Backtest first, but it unlocks the real prize: contrarian signals from 19 years of historical mispricings. Sequence: 1→7→8.

Optimize for P(rank=1) not EV — correct objective for pools. 56 rating systems + 19 years of ESPN data = infrastructure nobody else has.

Stop tuning plumbing, start mining the dataset.
